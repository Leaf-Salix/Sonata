Tutorial 5 - Storage Keys 与审计元数据

提问：Storage Key 解决什么问题？

在 IR 里，同一个内存位置可能有不同的变量名：

x = tensor.create(...)    # 分配了一块内存
y = foo(x)                # y 可能就是 x 的别名
z = bar(y)                # z 也可能是同一块内存

如果只看变量名，Sonata 会以为 x、y、z 是三个独立的内存位置。 实际上它们可能指向同一块物理内存。如果不知道一个 task 的参数存在哪块内存，就无法判断两个 task 是否访问同一块内存——即无法做 dataflow 依赖分析。

Storage Key 就是用来追踪"哪个变量名对应哪块物理内存"的机制。

提问：Storage Key 是怎么收集的？

collect_storage_keys 遍历 IR 节点，建立 var_identity → storage_key 的映射：

来源storage_key 格式例子
函数参数（param）param:<unique_id>:<name> 或 param:<name>param:0:x
tensor.create 分配alloc:<unique_id>:<name> 或 alloc:<name>alloc:y
函数调用的输出继承自写方向参数的 storage key同写入参数

回到 matmul_bias 的例子：

# task 0: matmul(x, w, y)
#   arg_storage_keys: ["param:0:x", "param:1:w", "alloc:y"]
#   → x 和 w 是入口参数，y 是中间分配

# task 1: add(y, b, z)
#   arg_storage_keys: ["alloc:y", "param:2:b", "param:3:z"]
#   → y 的 storage key 是 "alloc:y"，与 task 0 输出的 y 相同
#   → dataflow 分析发现：task 0 写 "alloc:y"，task 1 读 "alloc:y" → RAW 依赖

提问：TupleGetItem 是怎么处理的？

有些函数返回一个 tuple，然后通过 TupleGetItemExpr 取其中的元素：

result = multi_output_func(a, b)   # 返回 tuple
x = result[0]                      # TupleGetItemExpr
y = result[1]                      # TupleGetItemExpr

处理方式：

  1. multi_output_func 的每个写方向参数都有一个 storage key
  2. 这些 key 按顺序存在 tuple_element_keys 里
  3. 当遇到 result[0] 时，取第 0 个 key 给 x
  4. 当遇到 result[1] 时，取第 1 个 key 给 y

提问：Memory Storage Coverage 是什么？

Audit 元数据里有两个覆盖率指标：

"storage_key_coverage":           // 所有参数
    {"known": 6, "unknown": 0, "total": 6}
"memory_storage_key_coverage":    // 只有内存方向的参数（input/output/inout）
    {"known": 4, "unknown": 0, "total": 4}

eligibility 检查使用的是 memory_storage_key_coverage，因为只有内存参数影响依赖分析。上例中 6 个参数里有 4 个是内存方向，另外 2 个是 scalar/nodep 方向，不参与内存分析。

# 覆盖率 = 100% → dataflow 依赖分析完全可信

# 如果覆盖率低：
storage_key_coverage = {
    "known": 1,     # 只知道 1 个
    "unknown": 2,   # 2 个不知道
    "total": 3
}
# 覆盖率 = 33% → dataflow 分析不可靠，降级为 sequential
# 记录 warning，但不拒绝整个 Score（v0.1 阶段）

阈值：

  • STORAGE_COVERAGE_WARN_THRESHOLD = 0.5（50%）——低于此值产生 warning
  • STORAGE_COVERAGE_REJECT_THRESHOLD = 0.0（0%）——目前不自动拒绝，只警告

提问：Audit Metadata 还记录了什么？

build_score_metadata 生成的 metadata：

{
    "extractor": "structural_v0",
    "dependency_policy": "sequential_v0",    // 实际使用的策略（可能与请求的不同）
    "storage_key_coverage": {...},
    "memory_storage_key_coverage": {...},
    "entry_name": "my_function"
}

如果发生了 dataflow 降级，额外字段：

{
    "requested_dependency_policy": "dataflow_v0",
    "dependency_policy_fallback_reason": "dataflow_directions_unavailable"
}

如果有 nodep 方向的参数（不参与依赖计算的），也会被记录在 nodep_args 里，方便审计。
