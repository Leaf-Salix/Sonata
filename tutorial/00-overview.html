Tutorial 0 - Sonata 是什么？

提问：Sonata 要解决什么问题？

先说上下文。PyPTO 是一个面向昇腾 NPU 的深度学习编译框架。在 PyPTO 的世界里， 一个模型在执行前需要被编译成硬件能理解的指令。当前的调度方式是AICPU 动态调度。

AICPU（AI CPU）是昇腾 NPU 片上负责运行时图调度的 CPU 核心。它在运行时做三件事：

  • 逐节点分析依赖关系
  • 动态决定执行顺序
  • 分配和管理内存

问题是：每次推理都要重复这些工作。对于静态形状场景，这些工作完全可以提前到编译时完成。

类比：一个快递站有 100 个包裹，99 个地址清楚，1 个地址不清。 当前的做法是把 100 个包裹都按"地址不清"处理，全部人工派送。 Sonata 的做法是：先把 99 个地址清楚的包裹规划好最优路线直接派送，那 1 个地址不清的单独处理。

这个问题来自 PyPTO 的 Issue #1494：

"The current scheduling approach in PyPTO is AICPU-based dynamic scheduling. For static-shape cases, I would prefer not to use AICPU scheduling, but instead compile the scheduling directly on the host side."

Sonata 的目标就是实现这个 "host-side compiled calendar scheduling"——在宿主端提前编排好任务执行顺序，运行时直接按顺序执行。

提问：Score 是什么？

Score 是 Sonata 的核心产物——一个编译时提取的静态执行计划。它是纯 Python 数据结构，包含：

字段含义类比
name计划名称菜谱名字
runtime_target目标运行时配置用哪个厨房
tasks预计算的运行时任务菜谱里的每一个步骤
dependencies任务之间的依赖（DAG 的边）"必须先和面才能擀面皮"
shape_assumptions输入张量的形状假设"用 32 寸烤盘"——换了烤盘大小要重新规划
metadata审计/调试元数据—

提问：ScheduleContract 是什么？

ScheduleContract（调度契约）是 Sonata 的目标产物（v0.23+）， 一个 runtime-neutral 的执行计划。与 Score 不同，ScheduleContract 不绑定特定的运行时实现， 可以被不同的 backend consumer 消费：

  • HBG backend：使用 HostBuildGraph 验证 schedule 拓扑正确性
  • Sonata TensorMap Hybrid backend：生产环境的混合执行实现
当前状态：Score 是 Sonata 的当前产物，ScheduleContract 是未来目标。 两者的关系是：Score 描述"算什么"，ScheduleContract 描述"怎么调度"。

提问：Sonata 和 PyPTO 的关系是什么？

Sonata（本仓库）
  ├─ src/sonata/        ← Sonata 核心代码（纯 Python，不依赖 PyPTO）
  ├─ tests/sonata/      ← 纯 Sonata 测试（不需要 PyPTO）
  ├─ tests/pypto_cases/ ← 需要 PyPTO 的兼容性测试
  ├─ patches/pypto/     ← 给 PyPTO 的补丁
  └─ upstream/pypto/    ← PyPTO 上游（git submodule）

关键原则：Sonata 核心代码不 import PyPTO。 PyPTO 被当作"参考实现"和"测试用例来源"，而不是 Sonata 的内部组件。

提问：现在和未来是什么流程？

IR（Intermediate Representation，中间表示）是编译器领域的术语，指源代码和机器码之间的中间形式。 在 PyPTO 中，IR 是模型的图形表示，包含了所有的计算操作和依赖关系。

当前路径（AICPU 动态调度）：
  PyPTO IR → AICPU 运行时 → 逐节点分析依赖 → 动态分配内存 → 执行
                 ↑                                                        │
                 └──────── 每次推理都重复以上步骤 ─────────────────────────┘

Sonata 路径（编译时静态计划）：
  PyPTO IR → Sonata 提取 → Score (JSON) → Fingerprint → 缓存
              （编译时一次）                                  │
                                                             ▼
                                                 运行时直接消费 Score → 执行
                                                 （命中缓存则跳过提取）

提问：怎么动手试试？

方式 1：创建你的第一个 Score（5 行代码）

这是最简单的体验方式，不需要 PyPTO：

# 创建一个简单的 Score 对象
from sonata.score import Score, Task, Dependency

score = Score(
    name="my_first_score",
    tasks=[Task(task_id=0, func_id=0, core_type="aiv")],
    dependencies=[]
)
print(f"Score: {score.name}, {len(score.tasks)} task(s)")
# 输出: Score: my_first_score, 1 task(s)
恭喜！你刚刚创建了你的第一个 Sonata Score。 这个 Score 包含一个任务，没有依赖关系。 在实际使用中，Sonata 会自动从 PyPTO IR 提取这些信息。

方式 2：运行测试套件

如果你想验证 Sonata 的完整功能，可以运行测试：

# 确保 Sonata 已安装
cd pypto-sonata
PYTHONPATH=src python -m pytest tests/sonata -q

# 预期输出（类似）:
# 792 passed in 15.23s
提示：这个测试不需要 PyPTO，它使用模拟的 IR 对象来验证 Sonata 的核心逻辑。 如果你想了解 Sonata 如何处理真实的 PyPTO IR，可以阅读 Tutorial 7: 运行测试。
