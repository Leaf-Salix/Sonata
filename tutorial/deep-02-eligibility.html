Deep Dive 2 - eligibility.py 完整解析

本文件深入 src/sonata/eligibility.py 的每一个函数、每一条拒绝路径、每一个提取细节。 这是 Sonata 的入口模块——决定一个 IR 节点能否进入 Sonata。

模块总览

eligibility.py 是 Sonata 的最顶层模块，约 440 行。它的职责是：

  1. 检查 IR 节点是否满足 Sonata 的限制条件
  2. 如果满足，从 IR 中提取 Score（tasks + dependencies + shape assumptions + metadata）
  3. 如果不满足，返回结构化的拒绝理由

它依赖所有其他 Sonata 模块：score、storage、dependencies、audit、fallback，以及 pypto_adapter。

check_static_eligibility — 入口函数

def check_static_eligibility(
    node: Any,
    *,
    runtime_target: RuntimeTarget | None = None,
    entry_name: str | None = None,
    dependency_policy: str = DEPENDENCY_POLICY_SEQUENTIAL_V0,
) -> EligibilityResult:

参数详解

参数类型默认值含义
nodeAny（必填）IR 根节点。可以是 Function 或 Program
runtime_targetRuntimeTarget | NoneNone目标运行时。None 时自动用 host_build_graph
entry_namestr | NoneNone指定提取哪个函数。None 时提取所有 Orchestration 函数
dependency_policystr"sequential_v0"依赖策略。可选 "dataflow_v0"

执行流程（6 步）

步骤 1: 创建 adapter（PreMaterializePyPTOInputAdapter）
步骤 2: 检查根节点类型（必须是 Function/Program）
步骤 3: 遍历所有子节点，检查不支持的控制流/操作
步骤 4: 检查提取根是否存在、Group/Spmd 是否在范围内
步骤 5: 如果有拒绝理由，去重后返回
步骤 6: 提取 Score → 验证 → 检查存储覆盖率

关键设计：步骤 2~4 只收集拒绝理由，不立即返回。所有检查完成后一次性返回。 这使得调用方能拿到所有拒绝原因，而不是只看到第一个。

拒绝路径逐条解析

路径 1：根节点类型不支持

root_kind = _kind(node)  # type(node).__name__
if root_kind not in {"Function", "Program"}:
    → FallbackCode.UNSUPPORTED_ROOT_KIND

只接受 Function 或 Program 类型的根节点。其他任何类型（包括 object()）都会被拒绝。

路径 2：控制流不支持

_CONTROL_FLOW_KINDS = {"ForStmt", "IfStmt", "WhileStmt"}

if child_kind in _CONTROL_FLOW_KINDS:
    → FallbackCode.CONTROL_FLOW_NOT_SUPPORTED

遍历 IR 树的所有子节点（通过 adapter.walk(node)），只要出现任何一个控制流节点就记录拒绝理由。

注意：同一个类型的多个控制流节点会被去重。两个 ForStmt 只产生一条拒绝消息。

路径 3：RuntimeScopeStmt 不支持

elif child_kind == "RuntimeScopeStmt":
    → FallbackCode.UNSUPPORTED_RUNTIME_SCOPE

运行时作用域语句——PyPTO 在 MaterializeRuntimeScopes pass 中插入的 AUTO scope 包裹。 Sonata 的 certified dump 在这个 pass 之前，所以正常情况下不会遇到。但如果有人用了错误的 dump，这里会拦住。

路径 4：PyPTO adapter 范围外的节点

elif child_kind in adapter.unsupported_kinds:
    → FallbackCode.UNSUPPORTED_PYPTO_ADAPTER_SCOPE

这是 adapter 层面的拒绝——Submit、SpmdScopeStmt、ManualScopeStmt 等节点超出了 v0.1 adapter 的范围。

路径 5：tensor.read 不支持

elif child_kind == "Call" and _call_name(child) == "tensor.read":
    → FallbackCode.TENSOR_READ_NOT_SUPPORTED

只检查 Call 节点中 op 为 "tensor.read" 的特定操作。

路径 6：入口函数不是 Orchestration

if entry_name is not None and not extraction_roots:
    → FallbackCode.ENTRY_FUNCTION_NOT_ORCHESTRATION

当显式指定了 entry_name 但找不到对应的 Orchestration 函数时触发。

路径 7：Group/Spmd 调用超出范围

unsupported_call = adapter.has_unsupported_function_call()
if unsupported_call is not None:
    → FallbackCode.UNSUPPORTED_PYPTO_ADAPTER_SCOPE

v0.1 明确排除 Group/Spmd 函数调用——这些函数会把一个 Call 展开成多个 task（如 Group → AIC + AIV），超出了当前"一个 Call = 一个 Task"的提取模型。

去重逻辑

def _dedupe(reasons: list[FallbackReason]) -> tuple[FallbackReason, ...]:
    seen: set[tuple[str, str, str]] = set()  # (code, message, severity)
    ...

去重的 key 是 (code, message, severity) 三元组。完全相同的消息只保留一条。

Score 提取流程

当所有检查都通过后，进入 Score 构建阶段：

# 1. 确定 Score 名称
name = str(getattr(node, "name", "sonata_score"))

# 2. 通过 adapter 获取归一化事实
facts = adapter.normalize(storage_key_resolver=_storage_key_resolver)

# 3. 从 facts 提取 tasks
tasks = _tasks_from_facts(facts.functions)

# 4. 解析依赖策略（可能降级）
resolved_policy, fallback_code = _resolve_dependency_policy(tasks, dependency_policy)

# 5. 构建 Score
score = Score(
    name=name,
    runtime_target=runtime_target or RuntimeTarget(runtime="host_build_graph", ...),
    tasks=tasks,
    dependencies=build_dependencies(tasks, policy=resolved_policy),
    shape_assumptions=_extract_shape_assumptions(extraction_roots),
    metadata=build_score_metadata(...),
)

# 6. 验证 + 存储覆盖率检查
return _check_storage_coverage(score.validate())

_tasks_from_facts — 从归一化事实提取 Task

这个函数遍历 facts.functions 中的每个函数：

  1. 对该函数调用 collect_storage_keys 收集存储信息
  2. 对该函数调用 collect_call_output_vars 收集 Call 输出变量
  3. 遍历函数中的每个 call（已由 adapter 归一化）
  4. 按 call.callee_name 分配 func_id（首次出现时分配新 id）
  5. 从 call.arg_names、call.arg_directions、call.core_type 构建 Task
  6. 如果有输出变量赋值，传播 storage key

_extract_shape_assumptions — 形状假设提取

def _extract_shape_assumptions(nodes: tuple[Any, ...]) -> tuple[ShapeAssumption, ...]:
    assumptions: list[ShapeAssumption] = []
    multiple_roots = len(nodes) > 1
    for node in nodes:
        for param in getattr(node, "params", ()):
            symbol = _shape_symbol(node, param, multiple_roots)
            dims = _static_shape_dims(param)
            if symbol and dims is not None:
                assumptions.append(ShapeAssumption(symbol=symbol, dims=dims))
    return tuple(assumptions)

_shape_symbol 的三种返回

场景返回效果
参数名与类型名相同（匿名变量）None跳过该参数
单个提取根参数名（如 "x"）直接使用
多个提取根"func_name.param_name"（如 "main_a.x"）加函数名前缀避免冲突

匿名变量处理：如果参数没有名字（_arg_name 返回的是类型的 __name__，与 _kind(param) 相同），认为是匿名变量，跳过。

_static_shape_dims 的提取链

param → _param_type(param) → _shape_values(type) → [_const_int_value(dim) for dim in shape]

_param_type 尝试三个字段：type、type_、tensor_type。 _shape_values 尝试四个字段：shape、shape_、dims、dims_。 _const_int_value 先检查 dim 本身是否为正整数，再检查 dim.value（处理 ConstInt 包装）。

全部或无：如果某个维度无法提取（返回 None），整个参数的 shape assumption 被跳过。不会记录部分维度。这是为了保证 ShapeAssumption 的完整性——要么我们知道完整的形状，要么不知道。

_resolve_dependency_policy — 依赖策略降级

def _resolve_dependency_policy(tasks, requested_policy):
    if requested_policy == DEPENDENCY_POLICY_DATAFLOW_V0:
        code = dataflow_dependency_fallback_code(tasks)
        if code is not None:
            return DEPENDENCY_POLICY_SEQUENTIAL_V0, code  # 降级
    return requested_policy, None

降级条件：请求 dataflow_v0 但某些 task 缺少 arg_directions。 降级时 metadata 会记录 requested_dependency_policy 和 dependency_policy_fallback_reason。

_check_storage_coverage — 存储覆盖率检查

def _check_storage_coverage(result):
    # 只在 Score 验证通过后检查
    if not result.eligible or result.score is None:
        return result

    coverage = result.score.metadata.get("memory_storage_key_coverage")
    # 没有覆盖率数据或全部已知 → 不需要警告
    if not coverage or coverage["total"] == 0:
        return result
    if coverage["unknown"] == 0:
        return result

    # 覆盖率低于 50% → warning
    if coverage["known"] / coverage["total"] < 0.5:
        return EligibilityResult.accept_with_warnings(...)

    return result

注意：

  • 存储覆盖率检查在 score.validate() 之后执行
  • 只看 memory_storage_key_coverage（内存方向参数），不看 storage_key_coverage（全部参数）
  • 低于 50% 阈值产生 warning，但不拒绝 Score
  • 覆盖率 = 0 时不触发（因为 unknown == 0 意味着 total == 0，即没有内存参数）

辅助函数详解

_kind — 获取节点类型名

def _kind(node: Any) -> str:
    return type(node).__name__

返回类名字符串。这是 Sonata 结构化内省的基础——所有 IR 节点类型判断都通过 _kind 而不是 isinstance。

_call_name — 获取 Call 操作名

def _call_name(node: Any) -> str | None:
    # 尝试三个字段：op（字符串）、op.name、op_name
    op = getattr(node, "op", None)
    if isinstance(op, str): return op
    name = getattr(op, "name", None)
    if isinstance(name, str): return name
    op_name = getattr(node, "op_name", None)
    if isinstance(op_name, str): return op_name
    return None

兼容 PyPTO IR 的多种 Call 表示方式。op 可以是字符串（测试 mock）或对象（真实 IR）。

_arg_name — 获取参数名

def _arg_name(node: Any) -> str:
    if isinstance(node, str): return node          # 字符串直接返回
    name_hint = getattr(node, "name_hint", None)   # PyPTO IR 常用
    if isinstance(name_hint, str): return name_hint
    name = getattr(node, "name", None)
    if isinstance(name, str): return name
    return _kind(node)                              # 兜底：用类型名

当所有字段都找不到时，返回类型名——这会导致 _shape_symbol 判定为匿名变量并跳过。

_arg_directions — 获取参数方向

def _arg_directions(call: Any) -> tuple[str, ...]:
    directions = getattr(call, "arg_directions", None)
    if directions is None:
        attrs = getattr(call, "attrs", None)
        if isinstance(attrs, dict):
            directions = attrs.get("arg_directions")
    if not directions:
        return ()
    return tuple(_direction_name(direction) for direction in directions)

先查 arg_directions 属性，再查 attrs 字典——兼容两种 PyPTO IR 的方向存储方式。

_direction_name — 归一化方向名

def _direction_name(direction: Any) -> str:
    name = getattr(direction, "name", None)   # 枚举值
    if isinstance(name, str): return name
    value = getattr(direction, "value", None)  # 另一种枚举表示
    if isinstance(value, str): return value
    return str(direction)                       # 兜底

兼容 PyPTO 的枚举类型。不管底层是 Direction.Input、{"name": "Input"} 还是 "Input" 字符串，都能提取出方向名。

遗留函数：_extract_tasks 和 _extraction_roots

这两个函数仍存在于代码中，但主要的 task 提取路径已通过 _tasks_from_facts 和 adapter.extraction_roots() 替代。它们被保留用于向后兼容和测试。

双路径提取：当前代码有两条 task 提取路径：
  • _tasks_from_facts(facts.functions)：通过 adapter 归一化后的 facts 提取（新路径）
  • _extract_tasks(extraction_roots, core_types)：直接从 IR 节点提取（旧路径，测试用）
两者产生相同的 Task 结构，但新路径通过 adapter 解耦了 PyPTO IR。
