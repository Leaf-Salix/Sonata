Tutorial 6 - Fallback、解耦架构与工业界经验

提问：为什么需要结构化的 Fallback Reason？

当一个 IR 节点不能被 Sonata 处理时，需要告诉调用方为什么。 但直接用字符串做路由 key 有问题——如果错误信息改了措辞，下游代码就断了。 FallbackCode 枚举提供稳定的路由 key，不随消息措辞变化。

class FallbackCode(str, Enum):
    UNSUPPORTED_ROOT_KIND            = "unsupported_root_kind"
    CONTROL_FLOW_NOT_SUPPORTED       = "control_flow_not_supported"
    UNSUPPORTED_RUNTIME_SCOPE        = "unsupported_runtime_scope"
    TENSOR_READ_NOT_SUPPORTED        = "tensor_read_not_supported"
    ENTRY_FUNCTION_NOT_ORCHESTRATION = "entry_function_not_orchestration"
    SCORE_VALIDATION_FAILED          = "score_validation_failed"
    STORAGE_COVERAGE_BELOW_THRESHOLD = "storage_coverage_below_threshold"
    DATAFLOW_DIRECTIONS_UNAVAILABLE  = "dataflow_directions_unavailable"
    DATAFLOW_DIRECTIONS_INCOMPLETE   = "dataflow_directions_incomplete"

提问：FallbackReason 的结构是什么？

@dataclass(frozen=True)
class FallbackReason:
    code: str               # FallbackCode 的值（稳定，可作路由 key）
    message: str            # 人类可读的说明（可能变化）
    severity: str           # "error" 或 "warning"
    region_type: str | None = None       # v0.11: "static"/"dynamic"/None
    control_flow_node: str | None = None # v0.11: ForStmt/IfStmt/WhileStmt

EligibilityResult.reject 自动把 reason 字符串映射到 FallbackCode：

result = EligibilityResult.reject(
    "ForStmt is not supported by initial Sonata eligibility",
)
# result.reason_details[0].code     == "control_flow_not_supported"
# result.reason_details[0].severity == "error"

映射方式：code_for_reason 用子串匹配，顺序重要——更具体的模式必须排在前面。 当消息没有匹配到任何已知 code 时，用 _reason_code 生成一个 slug 兜底（不稳定，不建议作路由 key）。

提问：severity 的区别是什么？

  • error：Score 不合法，不能使用。对应 reject()
  • warning：Score 合法，但有降级信息。对应 accept_with_warnings()

警告场景：Storage coverage 低于阈值（但 > 0）、Dataflow 降级到 Sequential。

提问：Sonata 的解耦架构是什么样的？

Sonata 的一个关键设计原则是输入和输出都不绑定到特定的 PyPTO pass 阶段或运行时：

Sonata 解耦架构：
  PyPTO IR（经 pass pipeline 后的 certified dump）
    │
    ▼
  PyPTOInputAdapter（薄层，集中所有 PyPTO IR 字段访问）
    │                    ↕ 可替换
    ▼
  NormalizedTaskFacts（Sonata 内部表示）
    │
    ▼
  Score / eligibility / fingerprint
    │
    ▼
  RuntimeAdapter（薄层，映射到特定运行时 API）
    │                    ↕ 可替换
    ▼
  PlanHandle → 运行时执行

术语说明：

  • pass pipeline：PyPTO 编译器对 IR 进行的一系列变换步骤。每一步（pass）做一件事，例如推导调用方向（DeriveCallDirections）、生成运行时作用域（MaterializeRuntimeScopes）
  • certified dump：某个特定 pass 之后的 IR 快照。v0.1 默认绑定到 CollectCommGroups 之后、MaterializeRuntimeScopes 之前的 Simplify dump
  • NormalizedTaskFacts：Sonata 内部的任务事实表示（纯 Python dataclass），是 adapter 输出、Score 输入的中间格式
  • PlanHandle（v0.2 引入）：承载运行时执行所需的元数据。Score 管"算什么"，PlanHandle 管"怎么跑"
为什么这样设计：如果 PyPTO 改了 IR 字段名或插入了新 pass，只改输入 adapter； 如果运行时目标从 host_build_graph 切换到 tensormap_and_ringbuffer，只换输出 adapter。 Sonata core 不变。

输入侧选择 pre-materialize：接在 DeriveCallDirections 之后、MaterializeRuntimeScopes 之前—— DeriveCallDirections 产生 arg_directions（dataflow 依赖分析的前置条件）， 而 MaterializeRuntimeScopes 会引入 AUTO scope 包裹，Sonata 不需要处理。

输出侧选择 host_build_graph：PyPTO 最简单的静态运行时——add_task() 加任务、add_successor() 加依赖边，与 Score 模型天然接近。tensormap_and_ringbuffer 更复杂，留到 v0.3。

提问：其他系统是怎么做的？

上述设计不是凭空想的。在设计 Sonata 的过程中，系统调研了四个成熟系统：

系统Sonata 学到的核心经验
TorchInductor Guard 是"激活条件"，不是元数据——变了就要重新编译。
Graph break：遇到不支持的操作就切回 eager 模式。
Fingerprint 只覆盖计算身份，不覆盖执行元数据。
XLA / StableHLO 严格的计算 vs 执行分离：HloModule（计算）vs Executable（执行）。
形状合约：在模块入口验证，per-dimension 的 static/dynamic 区分。
Side-effect token 模型：用 token 对象强制安排没有数据依赖但有执行顺序要求的操作。
Apache TVM Compute/Schedule 分离：定义"算什么"和"怎么调度"是两件事。
两级内存规划：图级 liveness + 内核级 buffer 合并。
Any shape 类型 = per-dimension 的动态标记。
CUDA Graphs 录制前检查前提条件，回放时再检查——条件变了就回放失败。
两级失效：参数变了可以原地更新（便宜），拓扑变了必须重新录制（昂贵）。
编译时冻结内存计划，运行时不重新分配。
四系统共识：
  • 计算 ≠ 调度 — 所有系统都把"算什么"和"怎么跑"分开
  • Fingerprint = 计算身份 — 缓存键只看计算结构，不看运行时配置
  • Guard = 有效性域 — 每个 guard 条件定义了计划有效的前提
  • Fallback 是显式的 — 每个系统都有明确的 fallback 路径
  • 内存计划是编译时的 — 运行时不重新做内存规划
