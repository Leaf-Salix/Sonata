Deep Dive 1 - score.py 完整解析

本文件深入 src/sonata/score.py 的每一个类、每一个函数、每一个边界条件。 配合 tests/sonata/test_score.py 阅读效果最佳。

模块总览

score.py 定义了 Sonata 的核心数据模型，约 320 行代码。它是一个纯 Python 模块，不依赖 PyPTO IR 对象。唯一引入的 Sonata 内部依赖是 fallback.py（FallbackCode 枚举）。

模块中的类分为两类：

  • 数据模型（frozen=True dataclass）：RuntimeTarget、ShapeAssumption、Task、Dependency、FallbackReason、EligibilityResult、Score
  • 验证/辅助函数：Score.validate()、is_static_shape_dim、_find_cycle、_validate_task、_validate_shape_dims 等

RuntimeTarget — 运行时配置

@dataclass(frozen=True)
class RuntimeTarget:
    runtime: str = "tensormap_and_ringbuffer"
    function_name: str = "aicpu_orchestration_entry"
    aicpu_thread_num: int | None = 4
    config_comment: tuple[str, ...] = (
        "# Runtime configuration for tensormap_and_ringbuffer.",
        "# This runtime requires 4 AICPU threads (3 schedulers + 1 orchestrator on thread 3).",
    )

设计决策：RuntimeTarget 暂留 Score 内

已决定（路线 C）：RuntimeTarget 是执行元数据，不是计算身份。v0.1 暂留 Score.runtime_target 作兼容和审计字段；默认 score_fingerprint() 排除它。v0.2 引入 PlanHandle 后，将 RuntimeTarget 迁入 PlanHandle。

为什么现在不拆：直接拆出 RuntimeTarget 会扩大 v0.1 schema 改动范围。当前更重要的是先把 fingerprint 边界定稳。

切换条件：如果 runtime target 被证明会改变 computation semantics（而不只是执行包装），可考虑新增 execution-sensitive fingerprint API。

两种运行时目标：

Runtime含义Sonata 何时用
host_build_graphPyPTO 最简单的静态运行时，add_task() + add_successor()eligibility 默认，测试，v0.2 验证
tensormap_and_ringbuffer生产运行时，TensorMap + RingBuffer + 4 AICPU threads默认值（但 v0.1 不真正使用）

DEFAULT_RUNTIME_TARGET 是 RuntimeTarget() 的模块级实例，代表 tensormap 运行时默认配置。

ShapeAssumption — Guard 条件

@dataclass(frozen=True)
class ShapeAssumption(GuardCondition):  # 继承自 GuardCondition (v0.10+)
    symbol: str
    dims: tuple[int, ...] = field(default_factory=tuple)
    severity: GuardSeverity = GUARD_SEVERITY_HARD

Guard 语义

ShapeAssumption 同时是两个东西：

  1. 缓存条件：它参与 fingerprint 计算 → 形状不同 → 不同的 cache key
  2. 失效条件：运行时输入不满足假设 → Score / PlanHandle 应 fallback 或 replan

Guard 抽象（v0.10 已实现）

已完成（v0.10）：GuardCondition 基类已在 v0.10 引入，包含 severity（soft/hard）分级。 ShapeAssumption 现在是 GuardCondition 的子类，保持向后兼容但已 deprecated。 v0.11 进一步扩展为区域级 Guard 评估（GuardEvaluator.evaluate_region）。

Over-guarding 问题（v0.10 已解决）

已解决（v0.10）：100 个参数的 PyPTO IR 可能产生 100 个 ShapeAssumption， 使 fingerprint 极其脆弱。v0.10 引入 GuardSelector（默认 EntryParamGuardSelector） 从所有 Guard 中选出最重要的 Top-K，v0.11 进一步通过 select_region_guards() 支持区域级选择和密度检查。

Task — 原子执行单元

@dataclass(frozen=True)
class Task:
    task_id: int
    func_id: int
    core_type: str
    args: tuple[Any, ...] = ()
    arg_directions: tuple[str, ...] = ()
    arg_storage_keys: tuple[Any | None, ...] = ()
    name: str | None = None
    outputs: tuple[str, ...] = ()  # v0.11: 显式输出 buffer 的 storage key

task_id vs func_id 的区别

字段语义唯一性来源
task_id执行顺序编号——"第几个调用"Score 内唯一，非负extractor 按出现顺序分配（0, 1, 2, ...）
func_id函数类型编号——"调用哪个函数"可重复（同名函数共享）extractor 按首次出现的 call_name 分配

例如：

# 三个 matmul 调用 + 一个 add 调用
Task(task_id=0, func_id=0, name="matmul")  # matmul 第 1 次出现
Task(task_id=1, func_id=0, name="matmul")  # matmul 第 2 次出现（func_id 相同）
Task(task_id=2, func_id=0, name="matmul")  # matmul 第 3 次出现
Task(task_id=3, func_id=1, name="add")     # add 第 1 次出现（新 func_id）
func_id 对齐风险（#18）：Sonata extractor 按首次出现顺序分配 func_id，PyPTO codegen 用 func_name_to_id。两者可能不一致。v0.2 需要显式 FuncRegistry 映射 logical name → runtime id。

core_type 的三种值

值来源含义
"aic"PyPTO 函数的 func_type.name == "AIC"AI Core — 矩阵计算单元
"aiv"PyPTO 函数的 func_type.name == "AIV"AI Vector Core — 向量计算单元
"mixed"无法推断或两种都可能用到默认值

arg_directions 的五种值

值dataflow 含义storage 覆盖率影响
"input"读计入 memory_storage_key_coverage
"output"写计入 memory_storage_key_coverage
"outputexisting"写入已有缓冲区（in-place 输出）计入 memory_storage_key_coverage
"inout"读写计入 memory_storage_key_coverage
"scalar"标量，不参与内存依赖不计入（被 dataflow 忽略）
"nodep"不参与依赖计算不计入（被 dataflow 忽略）

注意：在 dependencies.py 的 dataflow 分析中，direction 会被 normalize 为小写无空格后匹配。"Input" 和 "input" 等价。

arg_storage_keys 的三种来源

格式来源例子
param:<id>:<name>函数参数（有 unique_id）param:0:x
param:<name>函数参数（无 unique_id）param:x
alloc:<name>tensor.create 分配的中间结果alloc:y

storage key 传播路径：参数 → tensor.create 分配 → 函数调用写方向参数 → 调用输出（AssignStmt LHS）→ TupleGetItemExpr 元素。详见 storage.py。

多输出 / TupleGetItem 传播

有些 PyPTO 操作返回 tuple（如 topk 同时返回 values 和 indices）。 v0.11 新增 Task.outputs 字段来显式跟踪这些输出 buffer：

# 一个返回 tuple 的 task
Task(
    task_id=2, func_id=1, core_type="aic",
    args=("x", "k"), arg_directions=("input", "scalar"),
    arg_storage_keys=("param:0:x", None),
    name="topk",
    outputs=("alloc:values", "alloc:indices"),  # v0.11: 显式声明输出
)

outputs 的作用：

  • Liveness 分析：compute_lifetimes() 会将 outputs 中的每个 key 视为一次写操作，精确计算 buffer 的 birth/death
  • 依赖分析：下游 task 读取这些 output key 时，能正确建立 RAW 依赖
  • 向后兼容：outputs 默认为空 tuple，不影响现有 task

Dependency — DAG 的边

@dataclass(frozen=True)
class Dependency:
    producer: int
    consumer: int
    kind: str = "data"  # "data" | "storage" | "war" | "ordering"

kind 的四种值

kind含义来源
"data"RAW（read-after-write）数据流依赖dataflow_v0 分析，或 sequential_v0 默认
"storage"WAW（write-after-write）存储冲突dataflow_v0 分析
"war"WAR（write-after-read）反依赖dataflow_v0 分析
"ordering"纯顺序约束，无数据流manual 或 fallback

sequential_v0 策略产生的所有边 kind 都是 "data"。 dataflow_v0 策略会根据 arg_directions 和 storage_keys 区分具体的 kind。

FallbackReason — 结构化失败原因

@dataclass(frozen=True)
class FallbackReason:
    code: str       # FallbackCode 的值（稳定路由 key）
    message: str    # 人类可读说明
    severity: str   # "error" 或 "warning"
    region_type: str | None = None           # v0.11: "static"/"dynamic"/None
    control_flow_node: str | None = None     # v0.11: ForStmt/IfStmt/WhileStmt

code 的两种来源

  1. 稳定枚举码：匹配到 FallbackCode 枚举值。可安全作路由 key。
  2. slug 兜底：未匹配时，由 _reason_code() 生成（字母/数字小写，其他替换为下划线）。不保证跨版本稳定。

_coerce_fallback_reason 的行为

EligibilityResult.reject() 和 accept_with_warnings() 都接受 str | FallbackReason 参数。_coerce_fallback_reason 统一处理：

  • 如果传入 FallbackReason 且 severity 匹配 → 直接复用
  • 如果传入 FallbackReason 但 severity 不匹配 → 创建新实例，保留 code 和 message，改 severity
  • 如果传入 str → 调用 _build_fallback_reason() 生成 slug code

EligibilityResult — 三态结果

@dataclass(frozen=True)
class EligibilityResult:
    eligible: bool
    score: "Score | None" = None
    reasons: tuple[str, ...] = ()
    reason_details: tuple[FallbackReason, ...] = ()

三种状态和它们的构造方式

状态构造方式eligiblescorereason_details 的 severity
完全合格accept(score)Truescore 实例空
合格但有警告accept_with_warnings(score, ...)Truescore 实例全是 "warning"
不合格reject(*reasons)FalseNone全是 "error"

accept_with_warnings 的 score 参数不能为 None（会 raise ValueError）。

has_errors() 和 has_warnings() 的行为

遍历 reason_details，只要有任一 severity 匹配就返回 True。空 reason_details 时两者都返回 False。

Score.validate() 的 10 项检查

validate() 是 Score 的一致性验证器。它返回 EligibilityResult：

#检查项错误消息FallbackCode
1name 非空score name must not be emptyscore_validation_failed
2task_id 唯一task ids must be uniquescore_validation_failed
3task_id 非负task id must be non-negative: Xscore_validation_failed
4func_id 非负task X func_id must be non-negativescore_validation_failed
5core_type ∈ {aic, aiv, mixed}task X has unsupported core_type: Yscore_validation_failed
6arg_directions 长度 = args 长度task X arg_directions size Y does not match args size Zscore_validation_failed
7arg_storage_keys 长度 = args 长度task X arg_storage_keys size Y does not match args size Zscore_validation_failed
8dependency producer/consumer 指向已知 taskdependency producer is unknown: Xscore_validation_failed
9无自环（producer ≠ consumer）dependency cannot be a self-edge: Xscore_validation_failed
10无环（DFS 检测）dependency graph must be acyclic, found cycle: 0 -> 1 -> 0score_validation_failed

注意 1：检查 #3 和 #4 会在 task_id 重复的情况下对同一个 task_id 多次报告。 测试 test_score_validate_accumulates_rejection_reasons 展示了这个行为。

注意 2：arg_directions 和 arg_storage_keys 只在非空时才检查长度。空元组（默认值）不触发检查。

ShapeAssumption 验证的 4 项检查

#检查项错误消息
1symbol 非空shape assumption symbol must not be empty
2symbol 唯一shape assumption symbol must be unique: X
3每个 dim 必须是正整数shape assumption X has negative/zero/non-integer dimension
4空 symbol 不检查 dim（跳过 dim 检查，只报 symbol 为空）

dim 错误去重：_validate_shape_dims 对同一个 symbol 的每种错误类别只报一次。例如 dims=(0, -1, "n", True) 只产生三条消息（zero、negative、non-integer），而不是四条。

重复 symbol 处理：遇到重复 symbol 时，先检查是否为第一个出现（检查 dim），再报告重复错误。第二个出现时不重复检查 dim。

环检测算法：_find_cycle

使用 DFS + 三色标记法：

# visiting: 正在访问的节点集合（灰色）——遇到灰色节点 = 发现环
# visited: 已完成访问的节点集合（黑色）——跳过
# stack: 当前路径栈——用于提取环的具体路径

关键细节：

  • 从 sorted(task_ids) 开始遍历——保证确定性输出
  • 后继节点也按 sorted 遍历——保证相同环总是返回相同路径
  • 环的格式：" -> ".join(str(task_id) for task_id in cycle)，如 "0 -> 1 -> 2 -> 0"
  • 自环（producer == consumer）在 validate() 的第 9 项检查中先被拦截，不会进入环检测

validate() 的 reason 转换

validate() 产生的所有 reason 字符串通过 _score_validation_reason 转为 FallbackReason：

def _score_validation_reason(message: str) -> FallbackReason:
    return FallbackReason(
        code=FallbackCode.SCORE_VALIDATION_FAILED.value,  # 固定 code
        message=message,
        severity="error",
    )

所有 Score 验证错误共享同一个 FallbackCode score_validation_failed。 下游无法通过 code 区分具体是哪项检查失败——需要看 message。

is_static_shape_dim — 形状维度判断

def is_static_shape_dim(dim: Any) -> bool:
    return isinstance(dim, int) and not isinstance(dim, bool) and dim > 0

这个函数同时被 score.py（验证）和 eligibility.py（提取）使用。 它必须拒绝的值：

输入结果原因
1, 64, 100000True正整数
0False零维度
-1, -100False负维度（PyPTO 用 -1 表示动态）
True, FalseFalsebool 是 int 的子类，必须显式排除
"n", 3.14, NoneFalse非整数类型
教训（mistakes/negative-dim-sentinel）：PyPTO 用 -1 作为动态形状标记。早期代码曾把 -1 当作静态值记录到 ShapeAssumption，导致 Score.validate() 拒绝合法的动态输入。修复：任何 dim ≤ 0 都视为动态/未知，跳过整个参数。
