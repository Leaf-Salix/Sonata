提问：什么是二进制 Schedule？

Sonata Schedule Contract 有两种序列化格式：

特性JSON (sonata_schedule.json)Binary (sonata_schedule.bin)
大小~3.5KB (10 tasks)~0.6KB (10 tasks) — 6x 更小
编码to_dict() + json.dumps()to_binary() — 紧凑的 C struct
解码json.loads() + from_dict()from_binary() — C 端直接读取 struct
人类可读✅ 是❌ 否（可用 hexdump 查看）
C 端解析需要 JSON 解析器零解析 — struct fields 直接内存对齐读取
完整性无校验CRC-32 校验 (v2+)
结论：二进制格式的主要优势在于 C 端可以直接通过 struct pointer 读取字段，不需要 JSON 解析器。同时占用空间减少 6x，附带 CRC-32 完整性校验。

提问：二进制格式的布局是什么？

二进制格式的内存布局和 flat_schedule.h 中的 C struct 一一对应：

Offset Size Field ────── ──── ────────────────────────────────── 0 4 magic (0x534F4E41 = "SONA") 4 4 version (1=v1, 2=v2 with CRC) 8 4 num_regions 12 4 total_tasks 16 4 total_args 20 4 total_deps 24 64 fingerprint (padded with \0) ────── ──── ────────────────────────────────── 88 4 [v2 only] CRC-32 of struct arrays ────── ──── ────────────────────────────────── 92 N FlatRegion[] (24 bytes each) 92+N M FlatTask[] (16 bytes each) ... FlatArg[] (6 bytes each) ... FlatDep[] (8 bytes each) ... String Table (optional)

所有 struct 使用 #pragma pack(push, 1)，因此不存在 padding 字段。 字段顺序与 C struct 声明顺序完全一致。

提问：如何生成和读取二进制 Schedule？

from sonata.schedule import (
    ArgBinding, ScheduledRegion, ScheduledTask,
    SonataScheduleContract,
)

# 创建 Schedule
t1 = ScheduledTask(task_id=0, kernel_identity="add", func_id=1,
    core_type="aic", args=(ArgBinding(arg_identity="x"),))
r0 = ScheduledRegion(region_id="r0", kind="static", tasks=(t1,))
sched = SonataScheduleContract(fingerprint="my_fp", regions=(r0,))

# 序列化为二进制（v2 带 CRC）
data = sched.to_binary()
print(f"Binary size: {len(data)} bytes")

# 反序列化（自动检测 v1/v2）
sched2 = SonataScheduleContract.from_binary(data)
print(f"Fingerprint: {sched2.fingerprint}")
print(f"Regions: {len(sched2.regions)}")

提问：什么是 Sonata Hook？

Sonata Hook 是一个极简的 C 接口，允许 PyPTO 运行时调用 Sonata 的 schedule 消费者：

#include "sonata_hook.h"

// 初始化（读取 SONATA_ENABLED 环境变量）
sonata_hook_init();

// 处理 schedule（验证 blob 并调用解释器）
const void *blob = ...;  // sonata_schedule.bin 的内容
size_t blob_size = ...;
int rc = sonata_hook_process_schedule(blob, blob_size);
// rc == SONATA_HOOK_OK      → 处理成功
// rc == SONATA_HOOK_SKIP    → 无可用 schedule，走原始路径
// rc == SONATA_HOOK_ERROR   → schedule 无效，走原始路径
// rc == SONATA_HOOK_DISABLED→ SONATA_ENABLED 未设置，跳过

// 清理
sonata_hook_fini();

提问：Fail-Open 机制如何工作？

所有 Sonata Hook 的失败模式都会优雅降级到原始 PyPTO 执行路径，不会 crash：

场景返回值Runtime 行为
SONATA_ENABLED 未设置DISABLED照常执行
sonata_schedule.bin 不存在ERROR照常执行
版本号不匹配ERROR照常执行
CRC 校验失败ERROR照常执行
数据截断/损坏ERROR照常执行
Guard 条件不满足SKIP照常执行

提问：St 测试中如何启用 Sonata？

# 直接运行 st 测试（启用 Sonata 分析）
PYTHONPATH=upstream/pypto/tests/st:src python -m pytest \
  upstream/pypto/tests/st/runtime/ops/test_abs.py \

# 4. 写入 sonata_schedule.bin（二进制 schedule）
# 5. 注入 RUNTIME_CONFIG["sonata"] + block_dim/aicpu_thread_num
# 6. dispatch_regions 输出优化统计

提问：如何验证 Sonata 确实在运行？

运行 st 测试时添加 --log-cli-level=INFO 可以看到 Sonata 的日志输出：

INFO  sonata.st_runner  RUNTIME_CONFIG['sonata'] injected into kernel_config.py

验证数据：

  • Sonata 端到端开销：在测量噪声范围内（预算 < 5%）
  • 二进制格式：6x 更小，C 端零解析
  • CRC-32 校验：from_binary() 自动验证

提问：Hook API 的成本是多少？

Hook 接口的设计目标是零成本抽象：

  • 当 SONATA_ENABLED 未设置时，process_schedule 立即返回 DISABLED，不做任何额外工作
  • Hook 是 C 接口，无 C++ 异常、无内存分配（调用方拥有 blob）
  • 性能基准测试显示开销在测量噪声范围内，满足 5% 预算
