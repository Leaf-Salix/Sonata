Tutorial 10 - 内存规划与约束求解

提问：内存规划要解决什么问题？

考虑一个 4 个 Task 的 Score：

Task 0: matmul(x, w)  → y     # 写 y
Task 1: add(y, b)     → z     # 读 y，写 z
Task 2: relu(z)       → a     # 读 z，写 a
Task 3: softmax(a)    → o     # 读 a，写 o

每个 Task 的输入/输出都是 buffer。这些 buffer 的生命周期不同： y 在 Task 0 写入、Task 1 读取后就不再需要了。 z 在 Task 1 写入、Task 2 读取后就不再需要了。

如果 y 和 z 的生命周期不重叠，它们可以复用同一块内存。 内存规划就是找出这种复用关系，减少 NPU 的内存占用。

类比：一个会议室（内存），不同时间段有不同的会议（buffer）。 两个会议如果时间不重叠，可以用同一个会议室。 内存规划就是安排哪些会议共用哪个会议室，使得需要的会议室总面积最小。

提问：BufferLifetime 长什么样？

用上面 4 个 Task 的例子：

compute_lifetimes(score) 的结果: BufferLifetime(storage_key="y", birth=0, death=1) └─ Task 0 写入，Task 1 读取 → 生命期 [0, 1] BufferLifetime(storage_key="z", birth=1, death=2) └─ Task 1 写入，Task 2 读取 → 生命期 [1, 2] BufferLifetime(storage_key="a", birth=2, death=3) └─ Task 2 写入，Task 3 读取 → 生命期 [2, 3] BufferLifetime(storage_key="x", birth=0, death=0) └─ Task 0 读取（输入参数） → 生命期 [0, 0] BufferLifetime(storage_key="w", birth=0, death=0) └─ Task 0 读取（输入参数） → 生命期 [0, 0] BufferLifetime(storage_key="b", birth=1, death=1) └─ Task 1 读取（输入参数） → 生命期 [1, 1] 时间线可视化: Task: 0 1 2 3 │ │ │ │ x: ■ w: ■ y: ■─────────■ b: ■ z: ■─────────■ a: ■─────────■ o: ■

冲突条件：a.birth <= b.death AND b.birth <= a.death （两个 buffer 在某个时间点同时存活）。

from sonata import compute_lifetimes, find_conflicts

lifetimes = compute_lifetimes(score.tasks)
conflicts = find_conflicts(lifetimes)
for c in conflicts:
    print(f"{c.key_a} 与 {c.key_b} 生命周期重叠")
# y 与 x 重叠（都在 Task 0 活跃）
# y 与 w 重叠
# z 与 y 重叠（都在 Task 1 活跃）
# z 与 b 重叠
# a 与 z 重叠（都在 Task 2 活跃）

提问：冲突矩阵是什么样的？

冲突矩阵是一个 NxN 的布尔矩阵，matrix[i][j] = True 表示 buffer i 和 buffer j 不能共享内存：

buffer 顺序: [x, w, y, b, z, a, o] 冲突矩阵（True = 不能共享内存）: x w y b z a o x [False, False, True, False, False, False, False] w [False, False, True, False, False, False, False] y [True, True, False, True, True, False, False] b [False, False, True, False, True, False, False] z [False, False, True, True, False, True, False] a [False, False, False, False, True, False, False] o [False, False, False, False, False, False, False] 解读: y 与 x, w, b, z 冲突 → y 不能和这 4 个共用内存 o 与谁都**不**冲突 → o 可以和任意 buffer 共用内存（它只在最后一个 Task 出现） 
from sonata.memory_plan import compute_conflict_matrix

matrix = compute_conflict_matrix(lifetimes)
# len(matrix) = 7, 每行 7 个布尔值

# stream 感知：不同 stream 的 buffer 不冲突
stream_ids = {"x": 0, "w": 0, "y": 0, "b": 0, "z": 1, "a": 1, "o": 1}
matrix = compute_conflict_matrix(lifetimes, stream_ids=stream_ids)
# z (stream 1) 和 y (stream 0) 不再冲突！
# 因为它们在不同 stream 上物理并行执行，内存独立

提问：plan_memory 怎么分配内存？

plan_memory() 使用贪心首次适配策略，用上面的例子逐步演示：

buffer_sizes = {"x": 100, "w": 200, "y": 300, "b": 50, "z": 300, "a": 200, "o": 100} Step 1: 按 size 降序排列 [y:300, z:300, w:200, a:200, x:100, o:100, b:50] Step 2: 逐个分配（找第一个不冲突的 offset） y (300): 没有已分配的 → offset=0 内存: [y:0-300] z (300): 与 y 冲突 → 不能从 0 开始 → offset=300 内存: [y:0-300] [z:300-600] w (200): 与 y 冲突 → 不能从 0 开始 → offset=300 与 z 冲突 → 不能从 300 开始 → offset=600 内存: [y:0-300] [z:300-600] [w:600-800] a (200): 与 z 冲突 → 不能从 300 开始 与 y 不冲突 → offset=0 可以！ 内存: [a:0-200] [y:0-300] [z:300-600] [w:600-800] （a 和 y 重叠区域 0-200，但 a 不与 y 冲突 ← 等等，a 和 y 确实不冲突！） 修正: a 只与 z 冲突。offset=0 不与 z 冲突（z 在 300-600）→ offset=0 可以 内存: [a:0-200, y:0-300] [z:300-600] [w:600-800] x (100): 与 y 冲突 → offset=300 与 z 冲突 → offset=600 与 w 冲突 → offset=800 内存: [a+y:0-300] [z:300-600] [w:600-800] [x:800-900] o (100): 与谁都**不**冲突 → offset=0（复用 a 的空间！） 内存: [o+a:0-200, y:0-300] [z:300-600] [w:600-800] [x:800-900] b (50): 与 y 冲突 → offset=300 与 z 冲突 → offset=600 与 w 不冲突 → offset=600 不行（与 w 重叠？w 在 600-800） → offset=800 不与 w 冲突 与 x 冲突 → offset=900 内存: [o+a:0-200, y:0-300] [z:300-600] [w:600-800] [x+b:800-900] 最终结果: peak_memory = 900 bytes 复用: o 和 a 共用 [0-200]，x 和 b 共用 [800-900] 
from sonata import plan_memory

buffer_sizes = {"x": 100, "w": 200, "y": 300, "b": 50, "z": 300, "a": 200, "o": 100}
plan = plan_memory(lifetimes, buffer_sizes)
print(f"Peak: {plan.peak_memory}")  # 900

# 查看每个 buffer 的分配
for alloc in sorted(plan.allocations, key=lambda a: a.offset):
    print(f"  {alloc.storage_key}: [{alloc.offset}, {alloc.end})")

提问：ConstraintSolver 和 GreedySolver 是什么？

v0.11 引入了可插拔的求解器架构。ConstraintSolver 是抽象接口， GreedySolver 是内置实现（和 plan_memory 同样的策略， 但接口不同——接受冲突矩阵而不是 lifetimes）：

from sonata.memory_plan import ConstraintSolver, GreedySolver, solve_memory

# GreedySolver 的接口
solver = GreedySolver()
plan = solver.solve(
    conflict_matrix=matrix,  # NxN 布尔矩阵
    sizes=[100, 200, 300, 50, 300, 200, 100],  # buffer 大小列表

print(plan.solver_type)  # "greedy"

提问：solve_memory 的超时和 fallback 是怎么回事？

# 复杂求解器可能在大图上超时
ilp_solver = ILPSolver()

plan = solve_memory(
    solver=ilp_solver,               # 先尝试 ILP
    conflict_matrix=matrix,
    sizes=sizes,
    device_memory_limit=1024 * 1024,  # 1MB 设备内存限制
    timeout_seconds=2.0,              # 超过 2 秒发警告
    fallback=GreedySolver(),          # 异常时用贪心
)
solve_memory 执行流程: ┌─ 开始 ─┐ │ │ │ try: │ ← 执行 ilp_solver.solve() │ │ ├─ 成功 ─┤ elapsed > timeout? → 警告 │ │ return result │ │ ├─ 异常 ─┤ → 警告 "Primary solver failed" │ │ → GreedySolver().solve() │ │ return fallback result └────────┘
注意：当前的超时是事后检查——求解器会完整执行， 超时只发出警告，不会中断。真正的中断式超时需要求解器自身支持。

提问：plan_memory 和 solve_memory 有什么区别？

plan_memorysolve_memory
输入BufferLifetime 列表 + buffer_sizes 字典冲突矩阵 + sizes 列表 + ConstraintSolver
策略固定的贪心首次适配可插拔（任何 ConstraintSolver）
超时无有（事后检查 + fallback）
Stream 感知无通过冲突矩阵（compute_conflict_matrix）
使用场景简单场景，快速原型生产环境，需要高级求解器

提问：完整的内存规划流程是什么？

from sonata import compute_lifetimes, find_conflicts, Score
from sonata.memory_plan import (
    compute_conflict_matrix, GreedySolver, solve_memory,
)

# 1. 计算 buffer 生命周期
lifetimes = compute_lifetimes(score.tasks)

# 2. 检查冲突
conflicts = find_conflicts(lifetimes)
print(f"冲突对数: {len(conflicts)}")

# 3. 构建冲突矩阵（可选 stream 感知）
matrix = compute_conflict_matrix(lifetimes)

# 4. 构建 sizes 列表（与 lifetimes 顺序对应）
sizes = [buffer_sizes[lt.storage_key] for lt in lifetimes]

# 5. 执行内存规划
plan = solve_memory(
    solver=GreedySolver(),
    conflict_matrix=matrix,
    sizes=sizes,
)
print(f"峰值内存: {plan.peak_memory} bytes")
for alloc in plan.allocations:
    print(f"  {alloc.storage_key}: offset={alloc.offset}")
总结：内存规划的目标是让 buffer 复用内存，减少 NPU 内存占用。 plan_memory 是简单场景的快捷方式； solve_memory + ConstraintSolver 是生产环境的可插拔架构。 贪心策略是可靠的 fallback，未来可接入 ILP/CP 求解器获得更优布局。
